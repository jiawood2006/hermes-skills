## 二、差距分析

### memory-graph（四维图谱：实体/时间线/因果/概念）
| 能力 | 同类谁有 | 我们原来 | 判定 |
|:--|:--|:--|:--|
| **记忆失效/遗忘机制** | cognee `forget()` | ❌ 无（只能手改 JSON 删） | **真缺口** |
| **多跳检索** | HippoRAG 核心卖点 | ❌ 只查单实体 | **真缺口** |
| 增量摄入 / 去重合并 | cognee / HippoRAG | ✅ 已有（别名自动合并） | 打平 |
| 一致性检查 / 伏笔追踪 | — | ✅ 已有（时间倒挂/线索未回收/别名冲突） | **我们独有** |
| n 元关系 | Hyper-Extract 超图 | ⚠️ 事件本身带多实体，够用 | 不补 |
| 社区检测 + 全局摘要 | graphrag | ❌ 无 | 不补（对本场景性价比低） |
| DB/服务化架构 | cognee / memU | ❌ 单文件 JSON | **有意为之**（可备份/可版本管理/零依赖） |

> **诚实说明**：单文件 JSON 打不过 cognee 的 DB 架构（大规模、多 agent 共享场景）。但本技能的定位是"**写作者自己用的长篇一致性工具**"，单文件反而是优点（能进 Git、能随手备份、能 diff）。**差距要补对的，不是补大的。**

## 三、本轮采纳项（已实现 + 实测）

### memory-graph v1.0.0 → v1.1.0
| 新增 | 对标来源 | 实测证据（构造 5 实体关系网） |
|:--|:--|:--|
| `retire <name> --reason --ch` / `revive`：旧设定弃用与恢复 | cognee `forget()` | `retire 军人父亲 --reason "改稿：父亲身份改为商人"` → `status` 显示「⛔ 已弃用: 1 个」；`query 陈骏` 关系行标 `⛔`；**历史关系完整保留** ✅ |
| `check` 新增「已弃用实体仍被引用」检查 | 同上 | 输出 `⛔ 已弃用实体「军人父亲」仍被引用: 陈骏（确认是否需改稿或恢复）` ✅ |
| `query --hops N` 多跳关系展开（含反向边） | HippoRAG multi-hop | `query 陈骏 --hops 2` → 第 1 跳 3 条（对手/恋人/父子）、**第 2 跳发现 `贺军生 --控制--> 老城区改造办`** ✅ |
| 幂等 + 别名解析 | — | 重复 retire 提示「已是 retired」；用别名「小陈」也能 retire/revive「陈骏」 ✅ |

> 这个功能的真实痛点：**改稿不能删旧设定**——读者看过、历史章节引用过。删了就查不出"旧设定还在正文里"的问题，标记失效才能既清理又留痕。

### memory-manager v1.0.0 → v1.1.0
| 新增 | 对标来源 | 实测证据（真实 1.2GB 会话库） |
|:--|:--|:--|
| `--corrections` 从会话历史挖掘纠正 + 标记「未记录/已在记忆」 | claude-reflect | 近 7 天扫出 **30 条候选**，含 9/6「以经营赚钱的方式和思路开展工作…你要记下」、9/10 方法论那条 ✅ |
| `--state-db` 升级为表级诊断 + 对症方案 | — | 实测发现 **872.6MB（71%）是 FTS 索引**（不是正文），给出"先重建索引、别急着删会话"的对症建议 ✅ |

**`--state-db` 的实测发现（本轮最有价值的意外收获）**：
```
🗄️ state.db: 1.2GB
   478.1MB  messages_fts_trigram_data     ← FTS 索引
   331.8MB  messages                      ← 真正的正文
   162.7MB  messages_fts_trigram_content  ← FTS 索引
   162.7MB  messages_fts_content          ← FTS 索引
```
原来的建议是"删 30 天前会话"——**方向错了**：删会话只能省 331MB，而索引占了 872MB。现在会先判断"大在正文还是大在索引"，再给对应方案。

## 五、方法论复盘

1. **"差距"要分性质**：本轮两项都**不是**功能数量差距，而是**生命周期缺口**——图谱缺"怎么死"（失效），记忆管理缺"怎么生"（从纠正中长出偏好）。**对标时要问：同类工具在解决什么生命周期问题，我们缺哪一段。**
2. **架构差异 ≠ 落后**：cognee/graphrag 是服务化大工程，我们是单文件小工具。**不能因为对方 ★ 多就照搬架构**——要判断对目标场景（写作者个人用）来说哪个更对。
3. **跑真实数据才能发现真问题**：`--state-db` 那个"71% 是索引"的发现，是拿真实的 1.2GB 库跑出来的——**光看代码永远不知道用户的实际瓶颈在哪**。
4. **有意的"不做"也要写下来**：自动写记忆、DB 化、超图——都写了理由。下次复看不用重新纠结。
