`resolution-cost-and-arrearage.md`、`resolution-cost-and-arrearage.md`），只管三件事：
**花钱之前怎么预检 → 生成锁什么分辨率 → 提交全挂时怎么判断是不是欠费。**
什么时候读它：① 用户问「测试用 720P 省钱、定稿再改 1080P 行不行？」「为什么这么贵？」；
② 准备提交一批分段之前（先过预检清单、先报单价）；③ 一批提交**全部**失败（尤其返回 `Arrearage`），

## 一、生成前预检清单（提交前逐项过，全是花钱前的免费动作）

1. **先看 prompt，不提交**（免费）：
   ```bash
   S=~/.hermes/skills/ecommerce/ai-video-ad-production
   python3 $S/scripts/make_ad.py $S/templates/ad_project.hsq1.json --steps plan
   ```
   确认产品锁 + 分镜无误再花钱。
2. **参考图必须公网可访问**：r2v 的 `reference_urls` / `media[].url` 只吃**公网 URL**。本项目托管：
   `https://yunvela.com/dh/` ↔ 服务器 `/opt/yunvela-site/dh/`
   ```bash
   scp a.jpg yunvela:/opt/yunvela-site/dh/ && ssh yunvela 'chmod 644 /opt/yunvela-site/dh/a.jpg'
   # 回读校验（不许跳过）：字节数 + md5 必须一致
   curl -s -o /tmp/dl.jpg "https://yunvela.com/dh/a.jpg?t=$(date +%s)"
   [ "$(md5 -q a.jpg)" = "$(md5 -q /tmp/dl.jpg)" ] && echo ✅ || echo ❌
   ```
3. **上传前先量「产品实体 高:宽」**（产品失真的真根因）：
   ```python
   a = np.asarray(Image.open(p).convert("RGB")).astype(np.int16)
   solid = a.min(axis=2) < 200            # 产品实体（排除白底与浅灰阴影）
   ys, xs = np.where(solid); print((ys.max()-ys.min())/(xs.max()-xs.min()))
   ```
   实测（HSQ1 迷你剃须刀，官方 74×39×39mm）：

   | 文件 | 实测高:宽 | 判定 |
   |---|---|---|
   | `正面图.png` | 625×1206 → **1.93:1** | ✅ 可用 |
   | `左侧图.png` | 627×1213 → **1.93:1** | ✅ 可用 |
   | 服务器旧 `hsq1_side.jpg` | **0.94:1（底面断面图：按键+Type-C 那面）** | ❌ 就是它把产品害成"矮胖罐" |

   **根因**：两张参考一张修长、一张圆胖 → 模型把两者**平均**。所以"产品每段都变形"**不是 prompt 写得不狠，是参考图自带矛盾**。
   → 换参考图前先量比例；两张必须**同向（都竖立）+ 同比例**。
4. **参考图制作**：按主体 bbox 居中裁方形（外扩 ~72%）→ 贴正方形**纯白**画布 → 缩到 1280×1280、quality 95。
5. **账号门禁自检**（欠费探测）→ 见 §四，提交前先跑一次空 input 探测。
6. **单价先报**（用户对成本敏感但不接受为省钱牺牲观感）；**长任务用 `background=true` + `notify_on_complete=true` 跑**，
   不要在 foreground 里 sleep 等待（**foreground 上限 600s**）。
7. 生成脚本坑：`submit_vN.py / build15_*.py / verify_*.py` **一律用 `write_file` 直接写文件**，
   **不要用 shell heredoc（`python3 - <<'EOF'`）拼**（`\n` 转义会被毁，本项目两次
   `SyntaxError: EOL while scanning string literal`，另一次 `re.sub(BODY…)` 把字典截断只写了 4739 字节）。
   改完先 `python3 -c "import ast;ast.parse(open('x.py').read())"` 验语法再提交。

## 二、分辨率口径（2026-09-18 A/B 实测定论）

**① 成片早就是 1080 了 —— 这一步 0 成本、已经在做。**
实测（ffprobe）：AI 生成源 `720×1280` → 装配器每段 `scale=1080:1920` → 交付成片 `1080×1920`；
字幕/花字/参数条/CTA 全部在 1080 画布上渲染。**"720P 生成 + 1080 交付"就是现状态。**

**② AI 视频换分辨率 ≠ 放大，而是重新抽卡。**
`parameters.resolution` 是**生成参数**，不是导出设置。改 1080P = 同 prompt **重新生成一遍**：
画出来的不是原来那条（机位、景别、人物、产品细节全变），等于全部重做 + 多花钱（1080P ≈ 720P 的 **1.7~2 倍**）。
所以"测试 720 → 定稿原生 1080"是**重做**，不是升级。

**③ 实测原生 1080P 更差**（同 prompt、同 5 张参考图、`wan3.0-video`、5s/9:16）：

| 项 | 720P 生成 → 装配升 1080 | 原生 1080P |
|---|---|---|
| 产品形态 | ✅ 等粗直筒、比例正 | ✗ 机头歪斜变形、几何不对 |
| 刀网 | ✅ 饱和香槟金 + 放射菱形网格 + 宽黑环 | ✗ **2.0s 那一帧变成暗灰黑圆盘（金色丢了）** |
| logo | ✅ 干净 Haier 一次 | ✗ 位置漂移、发软 |
| 锐度 | ✅ 干净利落 | ✗ **并不更锐**，反而更"塑料"、细节更糊 |
| 文件 | 5.7MB | 14.4MB（大 2.5 倍，画质无提升） |
| 构图 | — | ✗ 整条是**另一条片**（机位/景别全变） |

→ **定论（不必再赌）：全流程锁 720P 生成**。清晰度靠两条腿：
(a) 装配升 1080（现状，0 元）；(b) **产品特写/刀网用官方真像素素材**（原生 1080 清晰 + 100% 保真 + 近 0 成本）。
**门面镜（0–3s）也不要单独上原生 1080** —— 实测会上崩产品。

**❌ 已作废（2026-09-18）：为了"影棚感/更清晰"定稿改用原生 1080P 生成 → 现：一律 720P 生成，成片由装配器升到 1080×1920。**
（旧文 `resolution-cost-and-arrearage.md` §三的「影棚感版」提交参数 `duration:10 / resolution:1080P / ratio:9:16 /
watermark:false / prompt_extend:false` 与"只有万相 r2v（1080P，1 元/秒）能给这种观感"一句，按此作废。）

### 交叉印证：改分辨率会打坏产品（出处 `product-fidelity.md` §1）
同一角色、同一套 prompt，**只把 `parameters.resolution` 从 720P 改成 1080P**：

| 项 | 720P（此前一直用） | 1080P（本次改动后） |
|---|---|---|
| 机身长:径 | 1.82~1.97 ✓（真机 1.9） | **≈1.25 ✗（变矮胖罐/"易拉罐"）** |
| 顶部刀网 | 浅金色蜂窝网 ✓ | **退化成深灰平盖 ✗** |

执行规则：① 产品出镜的镜头默认 720P（0.6 元/秒，本来就比 1080P 便宜）；
② **任何分辨率 / prompt 改动后，必须重跑"逐镜 2 倍放大核产品 5 项"** —— "只改了分辨率、别的一字未动"仍然崩了，
所以"没动产品相关的内容"**不构成**跳过核验的理由；③ 别为"更清晰"盲目升 1080P：用户给的标杆样片实测只有 **544×960**，
真实感来自拍法（方向性实用光 / 真实皮肤 / 抓拍），**不是像素**。

### 首帧坑：参考图1 会被当成「画面首帧」
**症状**：三条不同钩子的开场 0.8 秒**长得一模一样** —— 全是同一张金网刀网微距。
**根因**：`wan3.0-video` 用 `input.images`（多参考图）时，**把参考图1 当作画面首帧**。我们把图1 设成"刀网微距（金色校准）"，于是每条片都从那张微距起步。
**修法**：要"开场就是他本人"→ **把图1 换成男主图**（代价：少一个金色校准锚点，刀网金色有变浅风险，换完必须重核刀网）。
**核验要求**：抽帧核验**必须含首帧（0.2~0.5s）** —— 只看中后段会完全漏掉这类系统性问题。

### 尺寸措辞的反向坑
正文里写"这台机器很小 / 长度不超过画面高度的六分之一"会把模型**往小里压** —— 这是用户反馈"**产品太小**"的**文本根因**。
→ 删掉这类倒向小的措辞，只留**正向下限**：*机身总长 ≈ 他手掌长的 1.1~1.3 倍、约占画面高度的 1/6、刀网黑环与金色网面清晰可辨*。

### 平台侧
抖音/快手竖屏会二次压缩，720→1080 在手机信息流里几乎看不出差别；观感来自光照、产品清晰度、字幕锐利度，不是分辨率数字。

## 三、计费与失败不计费

AI 视频**按秒计费** —— 1 秒 = 24~30 帧逐帧去噪，每帧跑整张大模型。所以成本 = **秒数 × 分辨率**。

| 720P 档 | 元/秒 |
|---|---|
| pixverse-v6-r2v-omni | 0.27（最便宜） |
| **wan3.0-video** | **0.6** |
| kling-v3-omni | 0.6 |
| wan2.7-r2v | 0.6 |
| vidu-q3-ad | 0.78 |
| wan2.1-vace-plus | 0.734 |

1080P ≈ **×1.7~2**；4K ≈ 3 元/秒。

**省钱四招（已落进 make_ad 工作流）**：① 全部 720P；② 全部无声（旁白后期 edge-tts 云希配）；
③ 只用 5 秒档（同一段能拆就拆）；④ **提交失败不计费**（prompt 超限/模型 id 写错这类错误是 0 成本，可以先探测）。

**失败/欠费期间一律不计费**：
- 欠费期间的 400 提交全部 0 元 → **充值后原样重跑**即可，不用改配置。
- 空 input 探测任务会被受理成 PENDING，随后 `InvalidParameter` 快速失败（实测 0.2s），**不计费**。
- r2v 一次 API 调用生成**一整段**（10s，含 3 个镜），**没有"只重跑某一个镜头"的选项** ⇒ 改一处 = 整段重来（0.6 元/秒 = 6 元/段 + 约 15 分钟）→ 先定位是哪一段哪一镜，**不要全片重跑**。

**A/B 归因的做法（别一轮一轮试）**：怀疑"分辨率还是 prompt 导致失真"时，**同一 prompt、同参考图、只差一个变量**，
两条**同时**提交（例：标准锁 × 720P vs 强化锁 × 720P），13 分钟一次拿到归因，并顺手得到一版可用成片；
720P 那版可直接复用已有产物 → 实际只花新生成那一条。对比只比**同一机位、同一时段**的帧，
避免把镜头间固有抖动误读成变量效应；把对比图（全帧 + 产品区 1:1 放大）发给用户看。
提交脚本按 `runid = 角色_分辨率[hard]` 命名任务与产物文件（如 `m_720p` / `m_720ph` / `o_720ph`），否则并发跑两版会互相覆盖 tasks json 和 mp4。

### 引擎切换（`make_ad.py` 已支持）
项目 JSON 里写 `"model": "wan3.0-video"` 即切换；字段差异：
- `wan3.0-video` → `input.images`（URL 列表）+ `parameters.watermark=false`
- `wan2.7-r2v` → `input.media:[{"type":"reference_image","url":...}]`

一次提交只能一个 duration → 5s 与 10s 的段要拆成两个项目（两个 runid）分别提交。

## 四、`Arrearage` 欠费排查（提交全失败时先看这里）

现象：一批分段提交**全部**返回
`{"code":"Arrearage","message":"Access denied, please make sure your account is in good standing"}`
—— 看起来像 prompt/模型 id 写错，其实是**账号余额不足**。别去改 prompt ✗。

### 免费探测（先做这个，再决定改什么）
```bash
K=$(tr -d '\n' < ~/.hermes/.dashscope_key)
# 空 input 探测：Arrearage = 欠费被拦；InvalidParameter = 已放行（只是字段/模型不对）
curl -s --max-time 40 -X POST "https://dashscope.aliyuncs.com/api/v1/services/aigc/video-generation/video-synthesis" \
 -H "Authorization: Bearer ***" -H "Content-Type: application/json" -H "X-DashScope-Async: enable" \
 -d '{"model":"wan3.0-video","input":{},"parameters":{"resolution":"720P","duration":5}}'
```

顺带一起探文本与图像（区分"整账号欠费"还是"某种模态"）：
```bash
# 文本：欠费时可能仍通（免费额度内）
curl -s -X POST "https://dashscope.aliyuncs.com/api/v1/services/aigc/text-generation/generation" \
 -H "Authorization: Bearer ***" -H "Content-Type: application/json" \
 -d '{"model":"qwen-turbo","input":{"messages":[{"role":"user","content":"OK"}]},"parameters":{"max_tokens":5}}'
```

区分「key 错」与「账号欠费」也可以用最便宜的文本模型探一次
`POST https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions` `model=qwen-turbo`：
- `Arrearage / overdue payment` → **整个账号**欠费（key 有效，不是模型权限问题，换模型也没用）
- `Incorrect API key provided` → key 本身无效/复制不全

### 判断与处置

| 探测结果 | 含义 | 处置 |
|---|---|---|
| 视频 `Arrearage`；文本/图像通 | **整账号余额不足**（文本/图像还在免费额度内，别被误导） | 充值，别改代码 |
| 视频 `InvalidParameter` | 已放行，只是字段/模型名不对 | 去修 payload |
| 全部 `Arrearage` | 账号级欠费/停用 | 充值（或检查是否充错账号） |

要点：
1. **换引擎没用** —— 可灵 / pixverse / vidu / VACE 全部跑在**同一个阿里云账号**下，一样 `Arrearage`。**不要浪费轮次换模型。**
2. 直达充值：`https://usercenter2.aliyun.com/finance/fund-management/recharge`
   （确认账号 = 你自己那个阿里云主账号——名下不止一个账号，**别充错**）。
3. **失败不计费**：欠费期间的 400 提交全部 0 元 → 充值后**原样重跑**即可，不用改配置。
4. 空 input 任务会被受理成 PENDING，随后 `InvalidParameter` 快速失败（实测 0.2s），**不计费**。
5. **❌ 已作废（2026-09-18）：充值后要等 ~30 分钟才恢复 → 现：充值即时生效**（实测本次充值后**立刻**放行）
   → 充完马上探测一次，通过就续跑，别空等。
6. 汇报口径：**结论 + 为什么（探测证据）+ 直达链接 + 建议充值额 + "充完回我一声，我自动自检并续跑"**。
   用户接受"你告诉我怎么开通我自己来"，但必须给他**直达链接 + 精确步骤**。
7. 纪律：消息/日志里**不贴 key**，`$K` 从文件读；探测命令里的 token 一律不外发。

### 用户说"已充值"但复测仍欠费 —— 三个高频原因
① 充到了**另一个阿里云账号**（另一家公司／另一个手机号／国际站 alibabacloud.com）
② 该账号有**未结清账单**（欠费状态要先结清，充值不一定自动抵扣）
③ 到账延迟（先等 1–2 分钟再复测，别急着下结论）

**解套办法（不必折腾退款）**：在**充了钱的那个账号**里开通百炼 → 建业务空间 → 生成新 key 交给助手，
本机只改 `~/.hermes/.dashscope_key` 一行即可接着干。

### 边界（别过度宣称）
- `/api/v1/quotas` **在欠费状态下仍可用**，能读到 `workspace_id`（本项目 `ws-1cv1h3gyburi5v9v`、业务空间 6034154），
  但**不含手机号/账号 ID** → **从 key 反查不出是哪个阿里云账号注册的**，别向用户承诺能查。
- 汇报时要说这是**账号计费状态**，充值/结清后**立即恢复**（同日已发生过一次恢复）。
  不要说成"万相不能用了/工具坏了"——那会把一次可修复的计费问题固化成拒绝服务。

## 五、成本估算示例（照上表单价折算）

- 25 秒片 = 5 次独立生成 ≈ **15 元**（0.6 元/秒 × 25s）。
- r2v 一段 = 10 秒 = **6 元/段**（约 15 分钟/段，含 3 个镜头，改一处就得整段重跑）。
- 30 秒片（3 段 × 10s）≈ **18 元**；若拆成 5 秒档可进一步省。
- 对比：实拍团队一条 15s 通常几千到上万；相对磁力金牛一天几百到几千消耗属零头。
- ❌ 已作废（2026-09-18）：`10s × 1080P = 10 元/段；两段 ≈ 20 元` 的"影棚感版"报价 → 现按 **720P 0.6 元/秒** 报。
